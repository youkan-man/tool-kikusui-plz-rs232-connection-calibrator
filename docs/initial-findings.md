# 初回現地調査結果

## 概要

4つのUSBシリアル経路を、読み取り専用SCPIクエリ`*IDN?`で調査した。

| 調査時のLinuxポート | USB変換器 | 結果 |
|---|---|---|
| `/dev/ttyUSB0`（root USB port 4） | CH340 `1a86:7523` | `KIKUSUI,PLZ-50F,0,1.09`を安定受信 |
| `/dev/ttyUSB1`（root USB port 5） | CH340 `1a86:7523` | 受信0バイト |
| `/dev/ttyUSB2`（root USB port 6） | FT232R `0403:6001`、serial `AB0KJQ0Q` | 返信ごとに23～24バイト受信するが文字化け |
| `/dev/ttyUSB3`（root USB port 7） | FT232R `0403:6001`、serial `BG04KVRV` | クエリは送信されるが受信0バイト |

デバイス番号は永続的ではない。物理配線との対応付けにはroot USB portと
`/dev/serial/by-path`を使用する。CH340変換器はシリアル番号を公開しないため、
`/dev/serial/by-id`では2台を一意に識別できない。

## 実施したテスト

- 公式対応速度: 2400、4800、9600、19200 bps
- 9600 bpsでのフレーミング／終端マトリクス:
  - 8N1, 8N2, 8E1, 8O1, 7E1, 7O1
  - LF, CR, CRLF
- `*IDN?`の反復問い合わせ
- XON/XOFF有効、無効、明示的XON送信
- 8800～10400 bpsの9600近傍走査
- 対応ドライバでのLinux `TIOCGICOUNT` UARTカウンタ
- USBトポロジ、重複露出、ポート所有プロセス、カーネルイベント

期待した動作を示したのは9600/8N1/LFだけだった。フロー制御の変更やボーレート微調整では、
文字化けするFTDI経路は正常化しなかった。

## 低レベルの根拠

文字化けするFTDI経路では、5回の問い合わせでおおむね次の増分を記録した。

- TX: +30 bytes
- RX: +118 to +120 bytes
- frame errors: +6 to +8
- BREAK: +5
- parity, overrun, and buffer overrun: unchanged

同じポートをクエリなしで5回開閉した場合、RX、frame、BREAKは増加しなかった。
したがってBREAKはポートを開いた時ではなく、計測器が返信した時に発生している。
変換器のレベルシフト、TTL/RS232変換器種別、ケーブル、コネクタ、GND、信号品質など、
RS232受信電気層の問題を示している。

もう一方のFTDI経路では、5回の問い合わせでTXが30バイト増えた一方、RXと全UART
エラーカウンタは0のままだった。ソフトウェアは送信できているが、UARTには受信データが
到達していない。

このカーネルのCH340ドライバは`TIOCGICOUNT`を実装していないため、2つのCH340経路では
ドライバのバイトカウンタを取得できなかった。

## USBトポロジ上の所見

直接root portに接続された設定済み変換器4台とは別に、QEMU USB hub配下にも一致する
未設定USBデスクリプタ4台が見えていた。未設定側はUSB configurationが`error -32`で
失敗している。シリアル試験中、直接接続側は安定していたが、将来の競合を防ぐためホスト側の
USBパススルー重複は解消すべきである。

## 推奨する物理切り分け

1. 正常と判明した変換器とヌルモデムケーブルへ、各PLZフレームを順番につなぐ。
2. 全フレームがその経路で応答すれば、異常側の変換器またはケーブルを交換・再結線する。
3. 文字化けするFTDI経路は、FT232R TTLケーブルではなく、レベルシフタを搭載した真の
   EIA-232製品であることを確認する。
4. ヌルモデム結線（DB9の2番と3番をクロスし、5番を直結）を確認する。
5. 物理修復後に`probe --strict`を実行し、安定した`/dev/serial/by-path`名を採用する。
   サービスユーザーには`dialout`グループまたは同等のudevルールでアクセス権を与える。
